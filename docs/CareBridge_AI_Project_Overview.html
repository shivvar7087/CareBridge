01 / Executive summary

What the project does

CareBridge AI is a web application for patients and caregivers coordinating the practical work that follows a hospital visit. It brings healthcare journey tasks, appointments, reports, documents, caregiver assignments, notifications, and access barriers into one workspace.

Clinical boundary: CareBridge AI is an organization and coordination tool. It does not diagnose, prescribe, or change a clinician's instructions. AI-generated extraction is a draft for patient review, and clinical wording is not editable by caregivers.

For patients

See the journey at a glance, track due and completed tasks, upload and review documents, manage reports, invite caregivers, assign selected tasks, and record barriers.

For caregivers

Accept an invitation, view tasks explicitly assigned to them, update task status, and see assignment history. Patient-only records and unassigned work remain outside their view.

For the care journey

Keep instructions connected to their source document, distinguish administrative progress from medical readiness, and make follow-up work easier to coordinate.

For deployment

Run locally with SQLite, or configure PostgreSQL for a hosted service. The React client and FastAPI API can be deployed separately.

Product principles

  • Patient review comes first: uploaded instructions do not silently become confirmed tasks.
  • Access follows relationships: caregivers see work only after invitation and assignment.
  • Administrative readiness stays administrative: a report checklist is not a clinical clearance indicator.
  • Fallbacks are explicit: without an AI provider key, analysis is labeled simulated and does not invent instructions.

Document review safeguards

  1. The user uploads a supported file. The API checks extension, MIME type, file signature, size, and ownership.
  2. Text extraction and analysis produce a reviewable record. AI analysis is not called until the patient has provided explicit consent.
  3. Proposed instructions are shown with their source context. Confirmation checks that task wording is supported by the source content.
  4. Confirmed suggestions are still labeled as needing verification where a clinician should review them.
OCR boundary: text-based PDFs are supported through PyMuPDF. Image OCR requires the Python Tesseract adapter and a system Tesseract executable. Scanned PDFs currently return an actionable unsupported-OCR response.
04 / Technical architecture

How the application is built

Frontend

React 18 with Vite, React Router, Axios, Tailwind CSS, Recharts, and Lucide icons. The frontend is a single-page application with responsive views and protected patient/caregiver routes.

Backend

FastAPI exposes JSON REST endpoints. SQLAlchemy handles persistence; Pydantic schemas validate API data. Alembic migrations support controlled schema updates.

Database

SQLite is the local default. PostgreSQL is configured through DATABASE_URL; hosted deployment is described around Render and a managed PostgreSQL database.

AI and OCR

AI provider settings remain server-side. Structured extraction uses an OpenAI-compatible endpoint. PDF text extraction and optional image OCR are separate adapters.

05 / Security and responsible use

Access, privacy, and clinical boundaries

Authentication

Passwords are stored as scrypt hashes. API sessions use signed, expiring JWTs. The secret key must be replaced with a strong value outside demo mode.

Authorization

Patient routes are scoped to the signed-in patient's records. Caregiver access requires an invitation and task assignment. Notification and document access are scoped to the owner.

File access

Uploads have type, signature, and size checks. Stored files are not exposed through a public URL; previews require authenticated ownership checks.

AI handling

Provider credentials stay on the backend. Analysis requires consent and remains a draft. When no key is set, simulated mode is clearly labeled and does not generate medical tasks.

Information that should not be inferred

  • A completed report checklist does not mean a patient is medically ready for treatment or discharge.
  • A model-generated explanation is not a diagnosis, recommendation, prescription, or substitute for a clinician.
  • In-app notifications do not imply an email, SMS, or messaging service sent an alert.
Production readiness: the included workspace is an MVP and uses fictional sample data. Before real patient use, configure private durable file storage, encryption, access controls, retention and deletion rules, monitoring, backups, provider terms, and applicable privacy/legal review. Do not use the demo workspace for real patient information.
06 / Running and deploying

Development and delivery

Local setup

  1. Use Python 3.11 or newer and Node.js 18 or newer.
  2. In backend/, create and activate a virtual environment, install requirements.txt, and copy .env.example to .env.
  3. Start the API with uvicorn app.main:app --reload --port 8000. It serves API information at http://localhost:8000/, health at /api/health, and API docs at /docs.
  4. In frontend/, install npm dependencies and run npm run dev. The client is served at http://localhost:5173 and calls the API at http://localhost:8000/api.

Configuration

SettingRole
DATABASE_URLSQLite by default; PostgreSQL URL for hosted use.
SECRET_KEYJWT signing secret; use a strong generated secret outside demo mode.
DEMO_MODESeeds fictional accounts and sample journey content when enabled.
CORS_ORIGINSBrowser origins permitted to call the API. Local demo mode supports localhost and 127.0.0.1 on port 5173.
AI_API_KEY / AI_MODEL / AI_BASE_URLOptional server-side structured extraction provider configuration.
UPLOAD_DIR / MAX_UPLOAD_MBLocal upload storage path and size ceiling.
VITE_API_URLFrontend API base URL, including the /api suffix.

Deployment model

The root Render blueprint defines the Python API service, a PostgreSQL database, and a pre-deploy Alembic migration. The React client can be deployed to GitHub Pages with its SPA fallback and a VITE_API_URL pointing at the deployed API. The backend CORS list must include the deployed frontend origin.

Uploaded documents use local storage by default. A production deployment should use private durable object storage and verify backup, retention, restore, and access-control behavior before enabling real document uploads.
